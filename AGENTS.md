# AGENTS.md -- adacovex

## Project

**adacovex** -- zero-dependency Ada/SPARK formal verification and compliance
toolkit for coverage analysis, proof verification, test-result parsing,
multi-standard safety-compliance assessment (DO-178C / ISO 26262 / IEC 62304),
and interactive dashboards.

- **Repo**: https://github.com/bladeacer/adacovex
- **Language**: Ada 2012 and later / SPARK 2014 (GNAT, Alire)
- **Zero library dependency**: uses only the GNAT runtime. gnatprove is *not* a
  declared dependency -- the `prove` subcommand resolves it at run time
  (per-project manifest, `$PATH`, `<data>/toolkit/`, or download) and
  lives only in the dev manifest for local task targets.
- **SPARK level**: Platinum is the target; the tree currently assesses at Gold
  because Platinum also requires full proof coverage (every subprogram the
  SPARK coverage report assesses proved). See
  [SPARK levels](docs/api-docs/adacovex-spark-levels.md).
- **Dashboard dependency view**: the served dashboard and the SBOM build from
  one resolved graph. A declared package keeps its base, dev, or test scope,
  a package only a lockfile names (Cargo.lock, poetry.lock, Gemfile.lock,
  composer.lock, package-lock.json, packages.lock.json, Package.resolved,
  pubspec.lock, mix.lock) is `transitive`, and a GitHub Actions workflow
  action (`uses: owner/repo@ref`) is a dev-scope `pkg:github` component. A
  licence expression (`Apache-2.0 OR MIT`) takes CycloneDX
  `license.expression`, never `license.id`. The graph includes system-tool
  dependencies as a first-class `system` scope (`pkg:generic/*`, shown with a
  `system` badge and no guessed link or licence -- only the resolved
  version). Tools that are really
  language packages are never system entries: the root project's Python
  requirements (`requirements*.txt`, for example sphinx and myst-parser)
  register as dev-scope `pkg:pypi/*` components with their version resolved
  from the package registry (`pip index versions <pkg>`). Vendored
  npm/pnpm (and cargo/pypi/composer) packages resolve their licence from the
  local manifest, or from the package registry (`npm view <pkg> license`,
  `pnpm show <pkg> license`, `cargo search <pkg>`) when the manifest is
  silent. Clicking a
  dependency in the Tree view or the nomnoml Diagram opens one split-view
  detail panel (view docked left, detail docked right; full width until a
  dependency is selected).

**System-tool scan scope**: only authored build files contribute a `system`
  tool, and only their command text counts: a tool named only in a comment
  never registers, while a leading `#!` shebang stays command text. A
  generated build tree (Meson, CMake, Ninja) records the developer's
  environment, `PATH` included, so `Skip_Scan_Dir` skips it by conventional
  name and by the build-system state inside it, and `Source_Tree_Hash` uses
  the same predicate for the tool-set cache key. The curated table is closed
  by decision (a tool absent from it never appears) and covers every build
  tool the committed fixture projects name.

**Keeping this file current:** before each change, check briefly whether
AGENTS.md still matches the codebase -- the source layout, the CLI flags, the
SBOM behaviour, and the dashboard features. Update it in the same change when
it has drifted; do not leave the architecture tree or the feature notes stale.

**User-facing surfaces:** the served dashboard HTML and the CLI `--help` / man
page are user-facing output. Never put developer-only commands (for example
`just prove`, `just check`, `alr build`) in dashboard prose or command help;
use the user-facing adacovex subcommands instead (`adacovex prove`,
`adacovex --help`). The man page is generated from the Ada source constants
(single source of truth); it stays in sync with the binary automatically.

**Documentation currency (LLM-assisted edits):** adacovex keeps user docs,
docstrings, and changelogs in step with the code. Stale docs are a release
blocker, never a follow-up. Every change that touches behaviour, flags,
tools, or output must also update, in the same change:

- the relevant user documentation under `docs/` (CLI reference, dashboard,
  platforms, architecture, developer guide, and so on);
- the Ada docstrings that feed `docs/api-docs` (regenerated by `just doc`);
- the release changelog under `docs/changelogs/` when the change ships in a
  release;
- `docs/contributing/perf/prove-timing.md` when a new version is added or
  its `just prove` figures change (see the phase rule below);
- `docs/contributing/ste100/index.md` when a new Technical Name enters the docs
  or docstrings.

**Proof-timing phases.**  `docs/contributing/perf/prove-timing.md` keeps the
`just prove` timing table as one column per **phase**, never one per release.
A phase is a range of versions whose implementation methodology is largely
similar (so far 1.55.0-1.56.0 (closed, rep 1.55.0), 1.57.0-1.60.0 (closed,
rep 1.58.0), 1.61.0-1.62.0 (closed, rep 1.62.0), 1.63.0- (open, rep 1.63.0)).
Fold each new version into the open phase while the methodology holds; close
the phase and open a new one on a methodology shift. Each phase carries exactly one
representative version, and the table uses that version's *complete* metric
set -- never the best value picked row by row from different versions in the
phase. When the metrics trade off, weigh them, choose the representative,
and state the reason in the page's reading notes.
Keep the table short: the page holds the three most recent closed phases plus
the open one, so a retired phase is deleted rather than kept. Before deleting
one, move whatever still explains a surviving number -- most often how the
warm syscall floor was reached -- into the "Across every phase" notes, so no
figure loses the reason it moved.

## Dogfood target

adacovex audits the Ada_CRDT library at `../Ada_CRDT` (`just run-ada-crdt`) and
its own source (`just run-self`, default target: cwd). `--target=PATH` points at
any Ada/SPARK project.

Self-assessment (`just run-self`) must always show:
- 100% docstring coverage (strict mode on by default, cannot be disabled)
- Gold SPARK level: 1060 VCs under gnatprove 16.1.0, 0 unproved, 0 justified
  (see `docs/proof/16.1.0-ledger.md`). Platinum additionally requires full
  proof coverage, which the SPARK coverage report does not show (subprograms
  in `SPARK_Mode (Off)` units stay outside the proof)
- 2489/2489 native tests passing
- DAL-C Achieved (and, via `--standard=all`, ASIL B + Class A Achieved;
  `run-self` emits `do178c.svg` / `iso26262.svg` / `iec62304.svg` badges)

The VC count lives in the docs and the proof ledger, never in the crate
description. `alire/long-description.txt` states the SPARK level alone, so a
past release's manifest never describes the current tree's proof surface.

## .adacovex patch directory

Strict mode (default) scans ALL directories except the always-excluded ones, so
vendored code counts against docstring coverage. A patch file at
`<target>/.adacovex/patches/<relative-path>` (a valid Ada `.ads` with docstrings
for the subprograms to document) overlays docstring info onto the matching
original without modifying it. Only active in strict mode.

The same patch file can carry **SPARK proof aspects** (`SPARK_Mode`, `Pre`,
`Post`, `Global`): the `prove` subcommand then merges them into a patched tree
copy (`<target>/obj/adacovex-proof/`) and proves the vendored code against it,
never touching the originals. A `.ads` patch re-declares the vendored spec
with contracts; a `.adb` patch opts the vendored body into the proof (bodies
are analysed only when they declare `SPARK_Mode => On`). How to write them:
[docs/contributing/proving-patches.md](docs/contributing/proving-patches.md#proof-patches-proving-vendored-dependencies);
the design: [docs/contributing/architecture-verification.md](docs/contributing/architecture-verification.md#proof-patches-spark-contracts-over-vendored-dependencies).

Full format, rules, and examples:
[docs/contributing/architecture-verification.md](docs/contributing/architecture-verification.md#patch-system).

Every flag has an explicit long spelling. The shorthands are `-t`
(`--target`), `-m` (`--manifest`), `-s` (`--serve`), `-p` (`--port`), `-c`
(`--cache`), `-b` (`--compare-base`), `-d` (`--coverage-delta`), `-l`
(`--level`, the GNATprove proof level -- never a compliance tier), `-r`
(`--require-proof`), and `-j` (`--jobs`). The bare words `serve`, `cache`,
and `relaxed` also select their flag. Long aliases: `--workers`
(`--serve-workers`), `--svg-path` (`--emit-svg`), `--emit-md` / `--md-path`
(`--emit-markdown`), `--no-md`, `--diff` / `--base` (`--compare-base`),
`--delta` (`--coverage-delta`), `--spark` / `--docstrs` / `--tests` (the
`--require-*` gates), and `--strict` (`--relaxed`'s inverse). Compliance
selection stays on `--standard` (which also accepts a combined tier token
such as `dal-B`, `asil-b`, or `class-c`) plus `--dal` / `--asil` /
`--class`. The alias set is expanded by `Normalize_Aliases` in
`src/core/adacovex-config.adb`; `Known_Flags` carries every alias so
completion and the typo suggestion know them.

`--fail-on=DIM[=VAL]` states the same thresholds as one CI policy flag
(`spark`, `docstrings`, `proof`, `tests`, `coverage`; comma-separated or
repeatable, a bare dimension reuses its `--require-*` value, and a bare
dimension with no threshold is an error). The `prove` subcommand always sends
a proof level: `--level=N` when the user gives one, otherwise 4, because
gnatprove without `--level` runs cvc5 alone with no per-check timeout. The
level is part of the option string and therefore of the proof result-cache
identity, so two callers of one project share one proof. A successful `prove` prints a
proof-coverage summary line by default -- statement, subprogram, and VC
coverage -- which `--no-coverage` hides for one run and `[prove] coverage =
false` in `adacovex.toml` hides for every run. The concise replay is
coloured by severity (`Adacovex.Ansi`, off under CI / `NO_COLOR` / a dumb
terminal) and cached as plain text, so a warm cache hit prints the same
warnings and diagnostics block as the fresh run it serves. Inside GitHub
Actions, each unproved finding also prints an inline `::error file=...`
annotation. Two configuration files are
read, with a fixed precedence: an explicit CLI flag wins, then the project
file at `<target>/adacovex.toml`, then the global file at
`<config>/adacovex.toml`, then the built-in default. The repository root
carries the sample `adacovex.toml`, and
[docs/usage/configuration.md](docs/usage/configuration.md) documents every
key.

Full flag reference, detailed behaviour, CI threshold gates (`--require-*`),
exit codes, the `sbom` subcommand, the per-standard level flags
(`--dal`, `--asil`, `--class`), and the `--standard` flag (including
`--standard=all`): [docs/usage/cli-reference.md](docs/usage/cli-reference.md).

`adacovex status` reports toolkit + platform state (Alire installed,
how adacovex itself is installed -- `source-checkout`, `alire-global`,
`on-path` -- plus the binary path, gnatprove
dependency-managed/detectable, CPU count, CI status, and which VCS
tools -- git/hg/svn/fossil/jj plus the man indexers mandb/makewhatis -- are
available for the differential modes plus the target's detected VCS) without
running an assessment or downloading anything: [docs/usage/platforms.md](docs/usage/platforms.md#status-subcommand).

`adacovex --version` prints the bundled version and exits. The version source
depends on the **installation method** (tools/gen-version.py resolves it and
regenerates `src/adacovex_version_info.ads`): `ADACOVEX_VERSION` (release
builds -- the shipped binary always reports the tag it was built from),
then `alire/alire-dev.toml` (source checkouts), then `alire.toml`
(dependency-managed installs: the toml associated with the covex binary for
dependency management carries the release version).

`adacovex man` installs the man page into a man root the host reader searches:
the first home-owned `$MANPATH` entry, otherwise the platform data root
(`$XDG_DATA_HOME/man` on Linux and the BSDs, `~/Library/Application
Support/man` on macOS, `%APPDATA%\man` on Windows); `--dir=PATH` overrides.
It refreshes the index with `mandb` (man-db) and falls back to `makewhatis`
(mandoc). When neither is available (or both fail) adacovex prints a warning
-- the page is still installed and readable via `man -l` -- and `adacovex
status` reports both indexers up front. The command also warns when the
chosen root is not on the reader's man path. The page embeds the version, and
`adacovex man --check` exits 0 when the installed page matches the binary (1
when a newer version is available or none is installed) -- so a shell prompt
hook can auto-update the man page when the machine detects a newer version.

`adacovex tldr` installs the bundled tldr page (`docs/tldr/adacovex.md`,
embedded via `tools/gen-tldr.py` into `src/adacovex-tldr_template.ads`) into
the detected local client: tealdeer's flat custom pages directory (from `tldr
--show-paths`, with the platform data rule as the fallback), or a base
client's cache pages tree (common plus the `linux` / `osx` / `windows` /
`android` / `sunos` / BSD platform page).`adacovex tldr --check` exits 0 when the installed page matches the bundled one, 1 when it
is missing or stale, and `--force` rewrites it. With no supported client the
command prints the page to stdout.

`--serve` watches the target by default (`--no-watch` turns it off): a polling
task rescans through the result cache and republishes document and package
metrics, and the page reloads from `GET /api/watch`. Proof, test, and
compliance panels keep the starting run's values.

`adacovex init [-t=PATH] [--force]` writes a sample `<target>/adacovex.toml`:
every supported key at its default, with the deployed configuration guide
linked. It never replaces an existing file without `--force`, and the global
key `[init] scaffold = false` disables it for every project on the machine. `just tldr-check` lints the page and gates
the embedded spec against it.

## VCS support (Linux, the BSDs, macOS, and WSL)

A **VCS is not required for base adacovex functionality**: scanning, proof
analysis, test parsing, compliance assessment, SBOM generation, dashboards,
and caching all work on a plain directory. A VCS is only needed for the
differential modes (`--compare-base` / `--coverage-delta`), which snapshot a
base revision -- and since adacovex audits *source code*, assuming the target
lives in a VCS is sensible.

adacovex runs on any platform that can run alire (Linux, the BSDs,
macOS, Windows, and WSL all qualify wherever Alire builds). The
differential modes (`--compare-base` / `--coverage-delta`) snapshot a
base revision without touching the working tree
across **git, Mercurial, Subversion, Fossil, and jj** (legacy codebases often
live in legacy VCS): git `worktree add`, hg `archive`, svn `export`, fossil
`open` on a copied DB, and jj via its internal git store. Detection is
marker-file based (`.git` / `.jj` / `.hg` / `.svn` / `.fslckout` / `_FOSSIL_`)
with a command-probe fallback. For VCS whose snapshot UX is poor (Subversion:
no local history, network-dependent; Fossil: niche tooling) adacovex prints a
note recommending the developers **convert the repo to git** (or a
git-compatible VCS) for the best experience. See
[docs/usage/vcs.md](docs/usage/vcs.md).

## Pipeline

Execution order: parse CLI -> scan -> patch -> doc metrics -> proof parse ->
test parse -> DAL assess -> render -> SVG/Markdown/SBOM -> serve -> exit code.
Step details: [docs/contributing/architecture-pipeline.md](docs/contributing/architecture-pipeline.md#pipeline-execution-order).
Early-exit modes run before the pipeline: `--help`, `--version`, `man`
(install/check the man page), `status`, `completion` (shell-completion
scripts), differential modes, and `sbom`.

## Key constraints

- Ada 2012 and later / SPARK 2014
- **Package/subprogram collections**: `Ada.Containers.Vectors` (heap,
  `Natural'Last` ~ 2.1B). No `Max_Packages` / `Max_Subprogs` limits. HLR tags,
  test metrics, and DAL failures are also unbounded vectors.
- **Fixed-size string buffers** remain bounded, and every width is one of
  five `Max_*` constants with one tier: `Max_Path` and `Max_Line` fail loudly
  (an overlong line or path is never truncated; the file is skipped,
  `Skipped_Ct` increments, and DAL becomes `Unmet`), and `Max_Id_Str`,
  `Max_Desc_Str`, and `Max_Filename` clamp with their length field. A bounded
  copy keeps no private width. See the overflow contract in
  [docs/contributing/architecture.md](docs/contributing/architecture.md).
- No library dependencies beyond the GNAT runtime (`Ada.Containers` is part of
  the standard Ada runtime). gnatprove is resolved at run time by the `prove`
  subcommand.
- **SPARK proof discipline** (enforced by `just prove` plus the
  `just spark-off-check` gate, both wired into `just check` and CI): every user assertion
  (`pragma Assert`, pre/postconditions, loop invariants) and every runtime
  check must be proved -- **0 unproved VCs**, **zero justified VCs**
  (no `pragma Assume` / `pragma Annotate` justifications), and **no
  `pragma SPARK_Mode (Off)` in `src/` except `Types.Implementation` and
  `Complexity`** -- the two packages that instantiate non-formal
  `Ada.Containers.Vectors`, which gnatprove rejects in `SPARK_Mode On` code
  (verified under gnatprove 16.1.0; see
  [docs/proof/16.1.0-ledger.md](docs/proof/16.1.0-ledger.md) for the
  evidence; `CPUs.Get_Temp_Directory` scopes a `pragma Warnings (Off,
  "no Global contract available")` around its runtime env-var reads so the
  run stays warning-free). I/O- and container-heavy
  bodies are default-off or SPARK-Mode-On-ensuring packages; they never carry
  an explicit Off pragma outside the two exempted packages.
- **New code must be fully SPARK-proven.** When adding code, introduce only
  `SPARK_Mode On` units that reach **0 unproved, 0 justified** under
  `just prove`. Do not add `pragma SPARK_Mode (Off)` for new code: the only
  packages permitted to carry it are `Types.Implementation` and `Complexity`
  (the non-formal `Ada.Containers` instantiations). If a new unit needs the
  container store, reuse `Types.Implementation` rather than opening a third
  Off package. Treat any `SPARK_Mode (Off)` outside the two exempt packages as
  a regression to remove on sight -- see `just spark-off-check`. The
  long-term plan is to hold `SPARK_Mode (Off)` at exactly these two packages
  (both irreducible: non-formal `Ada.Containers.Vectors` is illegal in
  `SPARK_Mode On` code under gnatprove 16.1.0); never let a third appear.
- **New code must also carry contracts covering
  each statement.** Every new executable statement in new or changed Ada code
  should be within a context with sufficient preconditions, postconditions,
  loop invariants, and runtime-check contracts so that `just prove` can prove
  the new code without unproved VCs. This is intended to prevent proof-coverage
  regression and avoid accumulating future proof debt. If a change cannot be
  proven in SPARK without widening the Off exceptions, do not widen them: narrow
  the change instead.
- **Python 3 is a build-time dependency**: it is required to bundle the
  dashboard and the offline manual into the binary via
  `tools/gen-dashboard.py` and `tools/gen-docs.py`. The pure-stdlib `tools/*.py`
  (version generation, description sync, test/proof doc sync, requirements
  sync, changelog checks, docs-tree, agents-tree) all run on Python 3;
  `tools/gen-docs.py` additionally needs `sphinx` + `myst-parser` + `furo`
  (single-sourced in `pyproject.toml`; `just requirements` renders the
  committed `requirements.txt`) to build the manual
  from `docs/`. The released binary itself embeds the manual as generated Ada
  string constants and has **no runtime Python dependency**.

## Tool scripts

`tools/*.py` are pure-stdlib Python 3 (no third-party packages) and annotate
all functions/variables with `typing` (`from typing import ...`). Keep new
scripts consistent: `typing` for annotations, `argparse` for CLI, `pathlib`
for paths, and no `pip install` / external imports. Run them with
`python3 tools/<name>.py`; the sync ones are wired as `just test-count`, `just
proof-status`, `just requirements`, `just docs-tree`, and `just link-check`
(markdown link
verification, run as a cheap static gate in `just check`).
`tools/tasks.py` is the task-runner entry point. The implementation lives in
`tools/taskkit/`: `common` owns paths, process helpers, and gate preflights;
`build` owns the build, proof, docs, and product tasks; `gates` owns the
cheap checks and sync targets; `e2e` owns the end-to-end suites; `release`
owns versioning and publishing; and `checks` owns `CHECK_GATES` and the
`check` runner. Two thin front ends call the entry point: the `justfile`
(`just <task>`, the primary developer runner) and the `Makefile` (a
compatibility shim that delegates each target, so an existing `make <task>`
reference in CI or the docs keeps working). The `check` gate order lives in
`tools/taskkit/checks.py`, and `tools/tests.py` reads `CHECK_GATES` from
there.
The multi-step tasks delegate their orchestration to dedicated
scripts so the runner stays declarative: `just build` runs
tools/build.py (version + dashboard regeneration, `alr build` with the
SFrame log filter, covex symlink),`just bench` runs tools/bench.py (hyperfine timings for the build phases -- the no-op build, a cold fresh-checkout build, both docs shapes, and a per-step generator breakdown read from `tools/build.py` and timed against the parallel bundle that build runs, with strace syscall profiles -- plus the pipeline and prove subcommand cold/warm timings and the stripped-binary size), `just doc` / `just fmt`
run their command through tools/dev-cmd.py (the alire-dev.toml swap,
restored unconditionally), `just coverage-gate` runs tools/coverage-gate.py
(temp-worktree docstring delta vs the previous release tag), `just prove` /
`just run-self` / `just sbom` / `just run-ada-crdt` all run through
tools/run.py (the single owner of the SOURCE_DATE_EPOCH + acceptance-gate
invocation shape; `run.py assess-args` feeds release.py), and `just
release` runs tools/release.py (`--dry-run` skips commit/tag/push; the
recipe refuses to start on any branch other than `main`, and the release
workflow refuses a tag whose commit is not on `main`).
The tools' own pure logic is covered by a stdlib-unittest suite whose runner
is `tools/tests.py`, wired as the `tools-check` gate in `just check`. The
test domains live in `tools/test_release.py`, `tools/test_docs_generation.py`,
`tools/test_docs_gates.py`, `tools/test_tasks.py`, and `tools/test_misc.py`;
`tools/testsupport.py` owns their shared imports and helpers.
`tools/check-action-parity.py` is a pure check (no writes) wired as
`just action-parity-check` -- a feature gate in `just check` and CI that
fails when the GitHub Action stops mirroring the base CLI option set.
`tools/check-version-consistency.py` is the sibling gate (`just
version-consistency-check`, also in `just check`): it fails when
`alire.toml`, `alire-dev.toml`, `src/adacovex_version_info.ads`,
`bin/adacovex --version`, or the committed `sbom.json` name different
versions. A version reaches each of those from a different source, so
they can drift; `just release` builds the release binary before it proves
so the binary under test is the one being released, and this gate catches
the residue tree-wide.
`tools/check-docs-coverage.py` is the sibling gate (`just
docs-coverage-check`, and the `ci.yml` `docs-coverage` job): it fails when a
CLI flag, a dispatched server route, or a hand-written usage/contributing
page is missing from the user docs.
`tools/check-test-layout.py` (`just test-layout-check`) keeps the test root
honest: every fixture under `src/tests/projects/` carries an `alire.toml`, a
GNAT project file, a `src/` tree, and a README, every contract-error class has
`case.toml` plus `broken/` and `fixed/`, and no workflow writes a project
inline with a heredoc.
`tools/check-test-portability.py` (`just portability-check`) flags a `/tmp`
path, a `/dev/null`, a hard-coded shell, a `chmod`, a `uname`, or another
host-specific shape in a test source, with a documented allow-list for the
few deliberate platform assertions. Both are feature gates in `just check` and
CI.
`tools/check-surface-parity.py` is the third gate (`just
surface-parity-check`, and the `ci.yml` `surface-parity` job): it fails when
the `--help` usage block, the man page SYNOPSIS, the cli-reference usage
fence, or a completion script stops advertising the parser's subcommand set,
when one of those surfaces shows a stale subcommand or flag, or when the tldr
description, the `--help` footer, the man DESCRIPTION, or the AGENTS.md
blurb drops the README tagline. The tldr page may advertise a subset (it is
a cheat sheet) and the README quick-start fence is a link-out summary, so
neither has to enumerate every subcommand -- they only have to stay true.
`tools/csslint.py` enforces the dashboard CSS 4px spacing rule (every
margin/padding/gap value a multiple of 4px); it is wired as `just
csslint-check`, run inside `just build`, and part of the `just check` cheap
gates. It is the pure-stdlib Python drop-in replacement for stylelint
(the dev tooling is Python-only by convention; no npm dependency is added),
and `tools/gen-dashboard.py` performs the equivalent CSS/JS minification at
build time. `tools/para-split.py` splits any paragraph that exceeds four
sentences into four-sentence paragraphs (the 4-sentence-per-paragraph rule is
enforced by `just docs-check` via `tools/check-docs.py`). It applies that
page's own sentence rule and paragraph segmentation, so it flags a file
exactly when the gate does, and it inserts blank lines only: it never cuts
inside an inline construct (a code span, a link, or a badge), and it keeps
the existing line wrapping at every line a break does not fall between. It
is a manual helper (not part of `just check`); the report names a paragraph
it cannot split without corrupting the Markdown.
`tools/check-docs.py` also enforces **one space after a sentence** (a `.`, `!`,
or `?` followed by two or more spaces and more text is an error) over the
docs, the changelogs, `README.md`, `AGENTS.md`, `CONTRIBUTING.md`, the
comment text of every `src/**/*.ads` / `src/**/*.adb` file, and the comment
text of every Ada patch file under `.adacovex/patches/` (a patch docstring
is prose too) -- a docstring is
prose too. An Ada line is read from its `--` marker on (a `--` inside a
string literal is not a comment), so code alignment is never flagged and
never rewritten; the generated units (`adacovex-docs_template`,
`adacovex-dashboard_template`, `adacovex_version_info`) are excluded, because
their generators emit single-spaced comments already and a hand edit there is
overwritten by the next `just build`. Its `--fix` mode collapses a double
space in exactly those places, so the gate and the fixer always agree.
`tools/rst2md.py` (wired as `just doc`) converts gnatdoc RST output into the
`docs/api-docs/` package pages + index; cross-links to the hand-written
reference pages live in its `GUIDE_PAGES` / `PACKAGE_GUIDES` tables, **never**
in `.ads` docstrings (gnatdoc parses comment text as RST and drops markdown
link URLs). gnatdoc emits no item description, so rst2md reads the docstring
prose itself and **fails the run** when a rendered item has no description, an
empty parameter row, or an empty Returns line.
`tools/gen-docs.py` (wired as `just book` and run inside `just build`) runs
`sphinx-build` over `docs/` (with `docs/conf.py`, the Furo theme, and the
MyST Markdown parser) and bundles the built site -- every page,
stylesheet, script, and badge -- into `src/adacovex-docs_template.ads` as a
path-keyed asset table (the bundled offline manual the `--serve` server
serves at `/docs`, where search works exactly as online). The spec also
carries the bundle fingerprint of the inputs it was built from
(`Source_Fingerprint`), so a tree with no Sphinx build directory -- a fresh
clone, or after the build output was removed -- keeps the committed spec
instead of rebuilding the site to reproduce the same bytes (~9 s of Sphinx
plus a full re-encode; now a 76 ms fingerprint read), and the bundled
`searchindex.js` is canonicalised (empty entries dropped, keys sorted) so
an incremental developer tree and the clean build a fresh clone runs emit
byte-identical bundles -- `--check` never takes the skip and still fails on
a stale or hand-edited spec. Every body is
gzip-compressed and then **base85**-encoded (the quote-free Z85 alphabet: 4
bytes to 5 characters where base64 needs 5.33), served with
`Content-Encoding: gzip` so the browser inflates it and the binary carries
no inflate routine. The Furo sidebar is not repeated per page: each page
keeps a stub and the toctree is stored once per branch under `_nav/`, filled
in by `resources/js/book-nav.js` (bundled as `_static/adacovex-nav.js`),
which also scrolls the open entry into the drawer without moving the page,
so navigation needs JavaScript exactly as search already did. Sphinx runs only
when the docs sources changed (a SHA-256 stamp of the source digests, the
fingerprint, and the output file list beside the build), and a changed tree
rebuilds **incrementally but verified**: only the changed pages are re-read
(their mtimes are refreshed first, so Sphinx cannot serve a stale doctree),
the outputs of a removed page are swept, and a navigation change (a page
added or removed, or a `{toctree}` edit) rewrites every page with `-a` so no
sidebar keeps a stale entry. The page set is then checked against the
sources, and a check failure falls back to a clean rebuild
(`tools/gen-docs.py --fresh` forces one), so a renamed or deleted page can
still never survive as a stale page in the bundle. The spec is written only
when its content changed, so a no-op build never rewrites it (a rewrite would
recompile the 28k-line unit and invalidate the cached proof). The SVG images
under `_images/` (the badge previews) ARE bundled, while the PNG screenshots
keep the note fallback. Each asset's gzip+base85 result is cached by SHA-256
under `obj/adacovex-docs-encode/` and the uncached bodies encode in parallel
across the CPU cores (`--jobs` caps the worker count at 8), so a docs edit
re-encodes only the pages it touched; both are pure speed-ups and the
emitted spec stays byte-identical. It is safe to
run without sphinx installed (the committed spec is kept); the same Sphinx
project powers the Read the Docs site (`.readthedocs.yaml`, installing
docs deps from `requirements.txt`).
`tools/check-book-links.py` (wired as `just book-links-check`, a cheap gate
in `just check`) verifies every link inside the bundled offline manual
(including the shared `_nav/` trees, whose links are relative to `_nav/`)
resolves against the bundled assets or the deliberately-not-bundled prefixes
shared with `tools/gen-docs.py` (`OFFLINE_EXCLUDED_PREFIXES`); the check
runs against a fresh `sphinx-build` from a temp copy of `docs/`, so a stale
local Sphinx build output (a gitignored build product) can never mask a
broken link.
The committed artifact is the generated spec itself, gated by
`python3 tools/gen-docs.py --check` (also in `just check`), so `docs/` edits
must be followed by `just book`.

## Workflows

GitHub Actions (composite `./action.yml` + `ci.yml` / `version-bump.yml` /
`release.yml`), action inputs/outputs, result caching, and release bundling:
[docs/usage/ci-cd.md](docs/usage/ci-cd.md). `ci.yml` runs the cheap quality
Gates, the build + native suite, and the self-assessment on a pull request and
a `main` push; `version-bump.yml` runs the macOS/Windows native suite when the
version in `alire-dev.toml` moves; `release.yml` runs the cross-platform build,
the composite-action regression, and the end-to-end suites on a release tag.
Every trigger and its jobs: [ci-scenario.md](ci-scenario.md).

Installation methods, target-project requirements, and running against another
project: [README.md](README.md#installing-adacovex).

### GitHub Action = base-CLI feature parity (feature gate)

**Action/CLI/docs parity is a feature gate, not a convention.**  The
`tools/check-action-parity.py` script enforces it and is wired into `just
check` (`action-parity-check`) and the `ci.yml` `action-parity` job, so a
drift between the base CLI, the composite action, and the docs fails CI.
The gate checks three directions against three sources of truth: the CLI
flags (`Known_Flags` in `src/core/adacovex-config.adb`), the action inputs
(the `inputs:` section of `action.yml`), and the docs/usage/ci-cd.md `### Inputs`
table. Every CLI flag must have a matching action input, every action input
must map back to a CLI flag, and every action input must be documented in
docs/usage/ci-cd.md (and vice versa). The mapping rules and the small, documented
allow-lists of deliberately non-CI flags (`CLI_ONLY` / `ACTION_ONLY` in the
script -- early-exit `--help`/`--version`, local dashboard `--serve` /
`--theme` / `--port`, `status`/`man`/`sbom` subcommands, `--out` /
`--emit-svg` output paths, and action plumbing like `build` / `run-tests` /
`result-cache`) live in the script; anything else must be wired end to end.
When a CLI flag is added, add the matching action input **and** its
docs/usage/ci-cd.md row in the same change -- or the gate fails.

Every CI run (the composite action and the `ci.yml` / `version-bump.yml` /
`release.yml` workflows) publishes a **Markdown summary** at the bottom of the
job page via `$GITHUB_STEP_SUMMARY`: the action appends an assessment table
(version, target, compliance, SPARK level, tests, coverage) plus an
`always()` run-summary step, and each workflow adds a `summary` job that
aggregates every job result. **Threshold failures fail loudly**: unmet
`--require-*` gates surface as `::error::` annotations, the assessment step
exits non-zero, the summary shows the unmet gates, and the workflow summary
job exits 1 when any job failed.

The composite action (`./action.yml`) mirrors the base CLI option set so CI
can drive every assessment feature the same way the binary does. The action
inputs map 1:1 onto the CLI flags (e.g. `target`/`--target`, `dal`/`--dal`,
`standard`/`--standard`, `asil`/`--asil`, `class`/`--class`, `manifest`/
`--manifest`, `relaxed`/`--relaxed`, `skip-dir`/`--skip-dir`, `no-svg`/
`--no-svg`, `no-cache`/`--no-cache`, `cache-dir`/`--cache-dir`, `cache-max`/
`--cache-max`, `cache-expiry`/`--cache-expiry`, `verbose`/`--verbose`,
`emit-markdown`/`--emit-markdown`,
`compare-base`/`--compare-base`, `coverage-delta`/`--coverage-delta`, the
`--require-*` gates, and the `prove-*` inputs onto the `prove` subcommand's
`--jobs` / `--level` / `--timeout` / `--steps` / `--memlimit` / `--force` /
`--no-loop-unrolling` / `--no-inlining` / `--counterexamples=on|off` /
`--quiet` / `--suppress-warnings=SETS` flags).

The `action-parity-check` gate above is what keeps these in sync -- a CLI
flag without its input, an input without its docs row, or a docs row without
its input all fail CI. The only assessment that is *not* reproduced in CI is
`just run-ada-crdt` (a local dogfood regression against `../Ada_CRDT`);
`ci.yml` runs the cheap quality gates, the native tests, and the
`--standard=all` self-assessment instead, `version-bump.yml` runs the
macOS/Windows native suite when the version moves, and `release.yml` runs the
cross-platform `platform-build` matrix, the composite-action regression, and
the end-to-end suites only when a release tag is pushed. Every gate job in
the workflows runs as plain Python
(`python3 tools/tasks.py <gate>`, the recipe `just <gate>` runs locally), so
a runner needs neither `make` nor `just`; the Ubuntu runner images ship
`python3`.

| Check | Command | Requirement |
|-------|---------|-------------|
| Unit tests | `just test` | 2489/2489 passing |
| Self-assessment | `just run-self` | 100% docs, Gold, DAL-C Achieved |
| SPARK proof | `just prove` | Gold (1060 VCs, 0 unproved, 0 justified under gnatprove 16.1.0), verified at `--level=4` (the deepest effort; the prove subcommand always sends a level -- the requested one, else 4 -- so the overhead is gnatprove's own) |
| Ada_CRDT regression | `just run-ada-crdt` | Stable against CRDT library (strict mode) |

**The true test of proof performance is the `prove` subcommand at the
binary level** (`./bin/covex prove`), not just the gnatprove level. The
warm shape is `./bin/covex prove` with the result cache populated (~55 ms;
stable across consecutive runs -- a `just prove` wall of ~1.0 s is the
no-op `alr build`, not the proof, because the generators write their Ada
specs only when the content changed since 1.50.0); the truly cold shape is
`./bin/covex prove --no-cache` with the result cache *and* the gnatprove
session store (`obj/gnatprove/`) wiped (61-88 s at 878 VCs on the dev
machine, dominated by the solver). `just bench` samples both with hyperfine
(prove-cold repetitions wipe `obj/gnatprove/` in their `--prepare`), plus a
fifth cold-clone scenario: prove against a fresh copy of the tree with no
cache, no session, and no `gnatprove.out` -- the first-run-on-a-new-checkout
shape. The prove result cache never serves a stored summary whose Total row
reports unproved VCs (a degraded run, for example one killed mid-session,
can store one because gnatprove exits 0 on solver timeouts); such a blob is
dropped and re-proved instead. The proof-input hash excludes the generated bundle specs
(`adacovex-docs_template.ads`, `adacovex-dashboard_template.ads`): they are
data-only string constants with no proof surface, so a docs or dashboard
edit never invalidates a cached proof.

[docs/contributing/perf/index.md](docs/contributing/perf/index.md); the
per-phase `just prove` timing table and its representative-version rule are
on

## Commit messages

adacovex uses Conventional Commits: `<type>(<scope>): <description>`.
Keep the subject up to 72 characters, start with a verb, end it without
a full stop, and use British English. Name the component from the scope
table in [docs/contributing/commits.md](docs/contributing/commits.md);
never invent a scope, and add its table row first in a `chore:` commit.
One component per commit: split the rest, explain why the change was
needed, and never repeat what the diff shows.

After you finish a change, always suggest the commit message and do not run
the commit yourself unless the user asks for it. Give the message in a
fenced block, state why the scope fits, name the version in `plan.md`
the change belongs to, and say whether the change needs a MAJOR
version. This rule applies to every LLM session that changes the tree.

**Atomic commits.** If the finished work is one atomic change -- one
component and one intent -- suggest one commit message. If it spans more
than one component or intent, do not force it into one commit. Name the
commits in dependency order and give one shell one-liner that stages and
commits them in succession, each with its own valid scope and its own
`git add` path set. A later commit in the chain must not need an earlier
commit's regenerated file unless that file is in the earlier commit.

The one-liner chains `git add` and `git commit -m "$(cat <<'EOF' ... EOF)"`
for each commit with `&&`, so a failed check or a rejected commit stops the
chain before the next component is staged. Keep the footer rules above at the
end of every message in the chain. Never run the one-liner unless the user
asks for it.

## Documentation

`docs/` is one Sphinx project (Furo + MyST) that Read the Docs builds and
`tools/gen-docs.py` bundles into the binary for the `--serve` manual at
`/docs`. There are two tiers: **user documentation** (`docs/usage/`,

assessment, and the **API reference** (`docs/api-docs/`) that `just doc`
generates from Ada docstrings. Never edit a generated page by hand.

**Currency rule.** A change that adds or alters a feature updates the page
that describes it in the same change. Route by the kind of change:

## Technical writing

All documentation uses British English spelling (for example: colour, organise,
licence, programme, centre, analyse) across the whole codebase, including user
docs, API docs, and Ada source docstrings. Spelling only; no other dialect
rules apply unless a section says otherwise.

User documentation follows ASD-STE100 Simplified Technical English. Use the
[SimpleEnglish skill](https://github.com/AminBlg/SimpleEnglish) for guidance. It is vendored
locally in [`./skills/simple-english/`](skills/simple-english/)(`SKILL.md` plus `references/word-swaps.md`, `references/use-cases.md`,
`references/checklist.md`) so adacovex dogfooding and CI need no network access
to apply ASD-STE100 rules. Load it from that path.

The controlled list of Technical Names (non-STE words approved for the
adacovex domain, with part of speech, definition, and banned synonyms) lives
in [docs/contributing/ste100/index.md](docs/contributing/ste100/index.md). Add any
new Technical Name to that list before you use it in documentation,
docstrings, or changelogs.

The skill enforces short sentences, active voice, one instruction per
sentence, consistent terminology, and no AI-slop hedging.

The API reference (`docs/api-docs/`) is generated by `just doc` from the Ada
source docstrings (gnatdoc + rst2md). Apply STE + British spelling to the
docstrings in the Ada source, not to the generated `.md` files. The
`docs/api-docs/index.md` landing page and the root `README.md` are exceptions:
keep them concise and British, but do not rewrite them to the full STE rules.

Third-party components get credit. Note each third-party project in
[docs/CREDITS.md](docs/CREDITS.md) and
[docs/THIRD_PARTY_NOTICES.md](docs/THIRD_PARTY_NOTICES.md). Do not drop
third-party attributions.
